# Catalog 存储认证设计（v3）：只留「两侧都能用」的路

> **状态：设计稿，未实现。** 配套原型 [`catalog-storage-auth-mockup.html`](catalog-storage-auth-mockup.html)。
>
> **v3 修订（2026-10-30）。** v2 把「这个 catalog 要不要给引擎写」做成表单上的一个开关
> （用途：只读 / 可写），并保留了「环境身份（不在 catalog 存秘密）」这一档。两处都撤掉：
> 前者把**授权模型该回答的问题**塞给了用户，后者与「catalog 必须能预览文件和数据」直接冲突。
> v3 只留一条判据——**一种认证方式必须同时喂饱服务端与引擎，否则不出现在表单里**。
> v1/v2 仍然成立的部分（六个功能各自的取票入口、`******` 哨兵与五条语义、前端不许算档位、
> 引擎续期责任表）保留并标「沿用」。

---

## 0. 一句话结论

**catalog 要能预览文件和数据，就必须有一份服务端自己拿得到、用得上的身份；而同一份配置还要供
Spark / Flink 使用。所以「支持哪些认证方式」不是偏好问题，是准入问题：三条线
（服务端读、服务端写、引擎读写）全部通过才可选。**

「用途」这一问因此消失——它问的是权限，而权限属于授权模型（`SELECT` / `UPDATE`），
不属于这个表单。同理，「不在 catalog 存秘密」也不能留：它把可读性交给部署，
而这一页的存在意义就是让配置在保存那一刻就能自证。

---

## 1. 三件事实，推出三条准入线

### 1.1 catalog 的六个功能都碰物理文件

| 功能 | 端点 / 触发点 | 动作 | 取票入口 | 缓存 |
| --- | --- | --- | --- | --- |
| 数据预览 | `POST /api/console/v1/tables/{tableId}/preview`（判 `TABLE:SELECT`） | 读 parquet + 读清单 | Paimon：`optionsFor`（**表级**）<br>Iceberg：`catalogOptionsFor`（**catalog 级**） | 不缓存 |
| 分区列举 | `GET /api/console/v1/tables/{tableId}/partitions` | 读清单 | 同上 | 不缓存 |
| 文件浏览 | `GET /api/console/v1/catalogs/{n}/files`、`GET .../tables/{id}/files` | `listStatus` | `catalogOptionsFor(catalog, false)` | 缓存短期票 |
| 文件下载 | `GET .../files/download` | 读流 | 同上 | 缓存短期票 |
| 元数据物化 | 建表 / 改表时写 `schema-<n>` | **写** | `optionsFor(..., allowWrite=true)` | 不缓存 |
| 删表目录 / 存储优化 | 管理 API、optimizer | **写** | `catalogOptionsFor(catalog, true)` | 缓存短期票 |

### 1.2 前两件事实：服务端既读又写

**读**是用户能看见的那一半（点开预览看不到就是看不到）。
**写**是没人注意的那一半：建表时 `TableMetadataService` 要往仓库里写 `schema-<n>`，
这一步用的是 `allowWrite=true` 的票。所以「只读 catalog」在对象存储上不存在——
除非写入由另一个 catalog 代劳，那已经不是同一个 catalog 的事了。

> 这一条推翻了 v2 的一个假设：v2 把「服务端写」当成能力矩阵里的一格，
> 于是「用途=只读」看起来可以让它不重要。其实它是**建表的必经路径**，
> 与用途无关，与有没有人点预览无关。

### 1.3 第三件事实：引擎侧也要同一份身份

Spark / Flink 与 catalog 是**两个进程、两套运行时**。catalog 上存的那份秘密要么直接交给引擎
（静态密钥），要么由服务端用它换一份短期凭据给引擎（签发）。两条路都得走通，
而这个 catalog 是不是要写数据，由**调用者的权限**决定，不由建 catalog 的人决定。

### 1.4 于是三条准入线

| 线 | 判据 | 不通过的后果 |
| --- | --- | --- |
| **L1 服务端可读** | 能对每个 `allowedLocations` 做 `getFileStatus` / `listStatus` | 预览、浏览、下载、分区列举全 500 |
| **L2 服务端可写** | 能对仓库根 `PutObject` | 建表 500；改表、删目录、优化任务全失败 |
| **L3 引擎可读写** | 下发的凭据能读也能写 | 读表正常、一 `INSERT` 就 403，报错位置在数据源算子 |

三条线**不是评分，是开关**。全过才允许出现在方式列表里；缺一条就是「不支持的认证方式」，
不是「支持但有个提示」。这是 v3 与 v2 最根本的差别：v2 允许存在「能用一半」的方式并给它一个红角标，
v3 认为那不该被建出来。

## 2. 为什么删掉「用途」

### 2.1 它问的问题已经有答案

v2 的用途开关想解决的是：签发档发出去的票只有读权限，用户要写就会在第一次 `PutObject` 拿到 403。
但「这张票该不该有写权限」在同一时刻已经有确定的答案了——**请求者的 `UPDATE` 权限**。
表单再问一遍，等于让建 catalog 的人替所有使用者的权限做决定，而这个人通常不知道谁会来写。

### 2.2 用户答错的代价是不对称的

| 用户选 | 实际需要 | 结果 |
| --- | --- | --- |
| 只读 | 只读 | 正常 |
| 只读 | 写 | 一小时后/第一次写才炸，报错在业务方 |
| 可写 | 只读 | 白挨一次红标，选不到最好的方式 |

两个错方向的代价一个是「静默坏」、一个是「多一条提示」。这种不对称的开关，删掉比留着重写文案更便宜。

### 2.3 正确的归属：票的权限跟着调用者走

```
引擎请求 ──▶ /token | loadTable | Lance storage_options
                  │
                  ├─ 调用者对这张表有 UPDATE → 发可写票（policy 覆盖读写）
                  └─ 只有 SELECT            → 发只读票
```

三个调用点都已经知道「是谁在请求」（bearer 身份），判一次权限即可，**协议形状不变**：
票里的 policy 变宽变窄，字段一个没多。

这一条落地之后，「引擎写」这件事不再需要用户回答，也不再需要界面上任何一处提示——
它和「这张表你能不能改」是同一个问题的两个说法。

> 落地注意：`CREATE TABLE AS SELECT` 是「建表 + 写入」两步，需要 `CREATETABLE` **和** `UPDATE`。
> 只给前者的用户会建出一张写不进的表。这不是 bug，是权限没给全；但报错必须点名 `UPDATE`
> （与 `USE_SECRET` 那条一样，错误信息写清缺哪个词比写「权限不足」有用得多）。

## 3. 为什么删掉「环境身份（不在 catalog 存秘密）」

### 3.1 它与「必须能预览」互斥

环境身份的含义是：catalog 上一个密钥都不存，服务端与引擎各自用自己进程所在环境的身份
（EC2 实例角色 / IRSA / Azure 托管标识 / GCS ADC）。问题在于**服务端进程有没有被这个桶认可的身份，
这个表单里没有任何一处能回答**。于是：

- 保存成功（配置合法）→ 打开预览 → `failed to list ...: null`（500）
- 用户从「保存成功」这一事实推出「应该能用」，实际从第一步就坏了

把「谁负责」推给部署方是可以的，但控制台这一页的职责是**让配置在保存前自证**。
留下这一档，等于在表单里开一个「我不知道」的选项。

### 3.2 它在引擎侧也常常不存在

「两边各自用自己的身份」听起来对称，落到真实部署里大多数是「两边都没有」：

| 引擎部署方式 | 有没有实例身份 |
| --- | --- |
| Spark on YARN（常见） | 没有；YARN 容器不继承 node 的 instance profile |
| Flink on Kubernetes 且未配 IRSA | 没有 |
| Spark on K8s + IRSA | 有（但要额外配 serviceAccount） |
| 本地 `spark-shell` | 只有开发者自己的 `~/.aws/credentials` |

也就是说这一档在文档上最安全（不存秘密），在实际环境里最容易变成未配置。

### 3.3 直接推论：IAM 角色必须带签名身份

删掉环境身份之后，「只填 `roleArn`、不填 AK/SK」这条配置也跟着失去意义——
它原来的行为是「用环境链去 AssumeRole」，正是环境身份的一种。

> **IAM 角色 = `roleArn` + 一对只授 `sts:AssumeRole` 的签名密钥。两个都必填。**
> 少一个就在表单里拦住（400，点名缺哪个字段），而不是让它退回环境链、
> 在界面上显示成「配置好了」。

`roleArn` 与静态密钥的语义差别因此必须写在字段旁边：配了 `roleArn` 时那对 AK/SK **不是**给引擎的钥匙，
而是服务端去 `AssumeRole` 时用的调用方身份。

### 3.4 代价，写在这里

| 代价 | 处理 |
| --- | --- |
| 存量里有大量「什么都不填」的 catalog | 不自动迁移，标为 `LEGACY_ENV` 只读档，编辑时强制补一种（§7） |
| `stsUnavailable` 这个 flag 仍存在于 DTO 与存量数据 | 保留读兼容，新表单**不再产生**它 |
| 云端纯 IAM 派发（不给任何密钥）的场景做不了 | 这是产品取舍：本工程的部署形态里，服务端与引擎都不是「桶主账号自己」 |
| Azure 托管标识 / GCS ADC 两种方式一起消失 | 同上；想用它们的人改用服务主体 / 服务账号 JSON，两者都能落在 catalog 上 |

## 4. 方式清单

### 4.1 按存储类型穷举（三线全过的才列）

✓ = 通过；—  = 不适用。**「今天能否选」是这一版最重要的列。**

| 存储 | 方式 | catalog 上存什么 | L1 | L2 | L3 | 今天能否选 |
| --- | --- | --- | --- | --- | --- | --- |
| **S3** | 静态访问密钥 | `accessKeyId` + `secretAccessKey` | ✓ | ✓ | ✓（引擎拿永久密钥） | 可 |
| **S3** | IAM 角色 | `roleArn` + 签名 AK/SK | ✓ | ✓ | ✓（票按调用者权限） | 等 S1 与 `s3-token` |
| **S3** | 临时安全凭证 | AK/SK + `sessionToken` | — | — | — | 灰卡不可选（G6 未实现） |
| **OBS** | 永久 AK/SK | AK/SK | ✓ | ✓ | ✓ | 可 |
| **OSS** | 静态 AccessKey | AK/SK | ✓ | ✓ | ✓ | 可 |
| **OSS** | RAM 角色 | `roleArn` + AK/SK | ✓ | ✓ | ✓（票按调用者权限） | 等 S1 与 `oss-sts` |
| **COS** | 永久密钥 | `secretId` / `secretKey` | ✓ | ✓ | ✓ | 可（COSN 无令牌位，永远没有临时档） |
| **Azure** | 服务主体 | `tenantId` + `clientId` + `clientSecret` | ✓ | ✓ | ✓（SAS 按权限位签） | 等 S1 与 `azure-sas` |
| **GCS** | 服务账号 JSON | `serviceAccountJson` | ✓ | ✓ | ✓（boundary 带写） | 等 S1 与 `gcs-downscope` |
| **FILE** | 本地文件系统 | 无凭据 | ✓ | ✓ | ✓ | 可（不探测） |

**三行是故意没有的**（DOM 里也没有）：S3 环境身份、Azure 托管标识、GCS ADC——
它们的取消是设计决定（§3），不是待办。

**两行是灰卡**：S3 临时安全凭证（缺 `sessionToken`）、OBS 的 IAM 委托
（`CreateTemporaryAccessKeyByAgency` 要账号 + 口令）。它们缺的是代码不是配置，
所以放在列表里、不可选、写明缺什么——灰掉比删掉更有用，因为「为什么没有这一档」
本身就是答案（§4.3）。

### 4.2 卡片上写什么：不写「能不能用」，写「密钥在哪、什么时候失效」

三线全过之后，所有卡片在「能不能用」上是**一样**的，那就不再是卡片该回答的问题。
真正的差别只有三处：

```
┌──────────────────────────────────────────────────┐
│ ○ IAM 角色                                        │
│   catalog 存一个 roleArn 和一对只允许 AssumeRole 的 │
│   签名密钥；每次取票现签一份，覆盖这次要读的表。      │
│   引擎拿到 短期票（≤12h，到期自动续）               │
└──────────────────────────────────────────────────┘
```

- **密钥的形态**：一对长期钥匙 / 角色 + 签名身份 / 服务账号 JSON
- **引擎拿到什么**：永久密钥 / 短期票（谁负责续期）
- **轮换时谁要动**：改 catalog 就够 / 改 catalog 且作业不用重启 / 两处都要改

第三个最容易被漏掉，而它决定了「钥匙到期那天要做什么」。

### 4.3 三种「不可用」，三种视觉（v2 的四种减成三种）

| 种类 | 视觉 | 例子 | 用户能做什么 |
| --- | --- | --- | --- |
| 本部署没启用 | 灰底 + 虚线 + 「本部署未启用」 | 填了 `roleArn` 但 `credential.providers` 里没有 `s3-token` | 找运维启用，或改选静态密钥 |
| 本工程没做 | 虚线 + 「暂未接入」+ 不可选 | S3 临时凭证、OBS 委托 | 只能看说明 |
| 这类存储永远没有 | **不出现在 DOM 里** | COS 临时密钥、Azure 账户密钥 | —— |

v2 的第四种「引擎写不可用（红色角标）」消失了：它由 §2.3 的写票覆盖，不再是用户要权衡的事。
红色角标留在界面上，会让人以为「我选错了」，而实际只是「票的权限还没做对」。

**存量还有另一个状态，但它不是「方式」**：`LEGACY_ENV`（§7.3）——一个横幅，不是一张卡；
它说的是「这个 catalog 目前什么都不满足」，而不是「有某种方式不可用」。

### 4.4 字段与三条服务端校验

字段组跟着方式走（切换方式只清凭据字段，`endpoint` / `region` 保留）。三条校验必须前后端同口径：

| 校验 | 文案要点 | 现状 |
| --- | --- | --- |
| `roleArn` 填了但缺 AK/SK（S3 / OSS） | 点名缺 `accessKeyId` / `secretAccessKey`，说明这对钥匙只用于 `sts:AssumeRole` | 已有 `secretFieldNameOf` 的同类机制 |
| Azure 缺 `tenantId` / `clientId` / `clientSecret` 任一 | 点名缺哪个，不要笼统「配置不完整」 | 部分已有 |
| GCS 的 `serviceAccountJson` 不是合法 JSON 或缺 `client_email` | 在表单里就拦，不要等换票时报 500 | 待补 |

`noInlinePolicy` 与 `stsUnavailable` 互斥那条 400 沿用（`StorageConfigs.validate`）；
新表单不产生 `stsUnavailable`，但存量编辑时它可能还在，冲突提示要照实说。

## 5. 保存前自检：读一档，写一档

### 5.1 为什么从一档变两档

v2 只做 `getFileStatus`，因为当时只要证明「服务端能读」。现在 L2 是必过线，
而**读得通完全不等于写得进**：

| 存储 | 读权限 | 写权限 | 两者是否同一份策略 |
| --- | --- | --- | --- |
| S3 | `s3:GetObject` + `s3:ListBucket` | `s3:PutObject` | 否 |
| OSS | `oss:GetObject` + `oss:ListObjects` | `oss:PutObject` | 否 |
| Azure | SAS 的 `r` / `l` 位 | SAS 的 `w` / `c` 位 | 是同一张 SAS，但权限位要单独签 |
| GCS | `storage.objects.get` | `storage.objects.create` | 否 |

只探读的行为，会让一个「能看不能建表」的 catalog 通过自检——而它连第一张表都建不出来。

### 5.2 契约（提案）

```
POST /api/console/v1/catalog-storage-probe
Authorization: 控制台会话；需 CATALOG:CREATE（新建）或 CATALOG:ALTER（编辑）

{
  "storageConfigInfo": { ... },          // 与保存时同一份草稿，含打码值
  "warehouse": "s3://bucket/paimon",
  "allowedLocations": ["s3://bucket/paimon"],
  "checkWrite": true                     // 默认 false；勾了才写
}

200 OK
{
  "verdict": "OK | DENIED | NOT_FOUND | UNREACHABLE | UNSUPPORTED",
  "serverReadable": true,
  "serverWritable": true,                // checkWrite=false 时为 null
  "checks": [
    { "location": "s3://bucket/paimon", "verdict": "OK", "detail": "HEAD 200" }
  ],
  "probeKey": "s3://bucket/paimon/_lakehouse_probe/20261030T1423-8f21c4.txt",
  "cleanup": true,
  "hint": null
}
```

`verdict` 取最坏的那个；`checks` 逐位置给，因为多位置时常是「第一个通、第二个不通」。

### 5.3 写档具体做什么

1. `PutObject` 一个 **0 字节**对象到 `<location>/_lakehouse_probe/<UTC 时间戳>-<随机6位>.txt`
2. `HeadObject` 确认它真的在
3. `DeleteObject` 删掉
4. 返回 `serverWritable` 与 `cleanup`

选这个形状的理由：

- **0 字节**：不占空间、不产生计费意义上的存储成本、也不会被误当成数据。
- **固定前缀**：桶策略只要放行 `_lakehouse_probe/*` 就能做「最小写权限」试跑；运维也容易清。
- **写完就删**：不指望桶的生命周期规则。删失败时 `cleanup=false` 并把 key 回给用户——
  残留一个 0 字节对象是可接受的，静默残留不可接受。
- **不写进仓库根**：`<location>/_lakehouse_probe/` 这个子目录不会被 Paimon / Iceberg 扫描，
  `warehouse` 下的清单文件列表不会多出异物。

### 5.4 判定映射

| 云侧现象 | `verdict` | 界面文案 | 常见原因 |
| --- | --- | --- | --- |
| 200 | `OK` | 可读（勾了写档且也 200 才说「可读写」） | —— |
| 401 / 403 `AccessDenied`（读或写） | `DENIED` | 这份身份没有权限，或根本没用上这份身份 | 密钥错、角色信任策略没放行、桶策略拒了、SAS 少了 `w` |
| 404 `NoSuchBucket` / 前缀不存在 | `NOT_FOUND` | 桶 / 前缀不存在 | 地址写错、region 不对 |
| 连接超时 / DNS 失败 | `UNREACHABLE` | 服务端连不上这个地址 | endpoint 填成内网地址、出网没开 |
| 没有对应 scheme 的 FileIO | `UNSUPPORTED` | 本部署没有这个 scheme 的实现 | `lakehouse.rest.file-io.type` 与插件 |

**403 与 404 在 S3 上不可区分**（无 `s3:ListBucket` 时 HEAD 一个不存在的 key 回 403）。
所以文案不写「对象不存在」，写「这个位置读不到：可能地址不对，也可能这份身份没有权限」——
两个都指向用户下一步要查的东西。

读通过、写失败是最常见的一种，且必须分开说：**「能读，不能写」**。
它对应的现象是「预览正常、建表 500」，不分开说，用户会以为整份配置都对。

### 5.5 安全边界（这一节比契约重要）

自检的本质是：**让服务端用调用方给的凭据，对调用方给的地址发一次请求。** 这已经是 SSRF 的形状：

1. **`FILE` 类型两档都不探。** 对 `file:///etc/passwd` 做 HEAD 就是一个「本机文件存在性」预言机。
   硬编码白名单，不是配置项。
2. **读档只 `getFileStatus`，不 `listStatus`、不读内容。** 列表能力等于把服务端变成对象存储浏览器。
3. **写档只写 0 字节，只写 `_lakehouse_probe/` 前缀，写完立刻删。** 不允许指定 key、不允许写内容。
4. **只探 `allowedLocations` 内的位置**，请求里另给的路径一律忽略。
5. **写档必须显式勾选**（`checkWrite=true`）。它会在对方的桶里真的创建对象，
   默认替用户做这件事不礼貌，也超出了「自检」这个词的语义。
6. **限频**：每用户每分钟 N 次（N 建议 6），失败也计数——否则它就是一个免费的凭据试错器。
7. **只回分类，不回原文**：云侧错误消息常带 endpoint、账号 ID、内网域名，只回上表五档。

### 5.6 自检 ≠ 授权

自检回答「服务端打开得了这个位置吗」；谁能看哪些行、哪些列要脱敏，是 `DataPolicyService` 的事
（见 `docs/data-policy-design.md`）。两者都在预览链路上，但认证失败是 500、授权不足是 403，
下一步动作相反，不许塞进同一个提示条。

## 6. 引擎侧

### 6.1 两层认证，别混

```
Spark / Flink ──① 到 catalog 服务端──▶ REST Catalog ──② 到对象存储──▶ S3 / OBS / ...
                 bearer / OAuth2                       本文的票
```

本文只管 ②。两层失败都长成 403，所以引擎片段里要把两段配置**分开列**，不要混成一大块。

### 6.2 续期：谁不续谁坏

| 方式 | 票的寿命 | 谁负责续 | 不续的后果 |
| --- | --- | --- | --- |
| 静态密钥 | 永久（`expireTimeInMs()==0`） | 不需要（但轮换要改 catalog） | 钥匙泄漏窗口不可控 |
| S3 IAM 角色 | 900–43200 秒（取 `min(TTL, 角色上限)`） | Paimon：`data-token.enabled=true`；Iceberg：`X-Iceberg-Access-Delegation: vended-credentials` + `client.refresh-credentials-endpoint` | 到点读表 403 |
| OSS RAM 角色 | 900–3600 秒（超出被夹紧） | **没有**——hadoop-aliyun 不换票 | 作业时长必须小于有效期 |
| Azure 服务主体 | SAS 有效期（平台上限 7 天） | **没有标准续期端点** | 同上 |
| GCS 服务账号 | 1 小时 | **没有** | 同上 |

**Flink 比 Spark 更需要这条**：批作业跑完就结束，流作业会跨过任意多个 TTL。
一个 `TTL=1h` + 没配续期的 Flink 流作业，在第 61 分钟开始报 403，而报错位置在数据源算子。

所以「方式」这个选择必须同时产出**客户端配置清单**（复用 `console/src/utils/engineSnippet.js`），
不能只产出服务端配置。

### 6.3 票的写权限（S1，L3 的前提）

三参 `vend(storage, tableId, tablePath)` 今天硬编码 `allowWrite=false`；服务端自己那条路
（`optionsFor(..., allowWrite=true)`）已经是分开的。要做的只是把调用点那一侧的意图传进来：

| 调用点 | 判据 | 传什么 |
| --- | --- | --- |
| Paimon `/token` | 调用者对该表有 `UPDATE` | `allowWrite` |
| Iceberg `loadTable`（委派）/ `.../credentials` | 同上 | `allowWrite` |
| Lance `storage_options` | 同上 | `allowWrite` |

风险与 P2-3 记录的是同一个：`loadTable` 之后客户端可能长期缓存这张票，
某人被收回 `UPDATE` 后，手上的写票还能用满一个 TTL。缩短 TTL 能收窄，撤销不能。

### 6.4 方式还会影响授权（容易被漏）

静态密钥方式发给引擎的是**长期密钥**，因此取票时要 `USE_SECRET`；
签发方式发的是短期票，只要 `USE_CREDENTIAL`。两个权限点是并列的（P1-7）。

于是「选静态还是选签发」不只是安全偏好，它还决定了：

- 使用者需要被授 `USE_SECRET`（多一个、且是更危险的一个）
- 升级到 P1-7 之后，只给了 `USE_CREDENTIAL` 的部署在用静态的 catalog 上会 403

引擎片段里必须写明这条，否则迁移时会变成一场「昨天还能跑」的排查。

## 7. 存量 catalog 怎么办

### 7.1 六类存量，两种命运

| 存量形态 | 今天的行为 | 映射到 |
| --- | --- | --- |
| 都没填（`NONE`） | 引擎用自己身份；服务端大概率 500 | `LEGACY_ENV` |
| `roleArn` + 有密钥，provider 未启用 | 转发那对长期密钥 | **静态访问密钥**（无损：配置里就是一把钥匙，行为就是转发） |
| `roleArn`，无密钥 | 环境链去 AssumeRole | `LEGACY_ENV`（不可无损映射） |
| `stsUnavailable=true` + 有密钥 | 转发 | **静态访问密钥**（无损） |
| `stsUnavailable=true`，无密钥 | 环境链 | `LEGACY_ENV` |
| Azure 无服务主体 / GCS 无 SA JSON | 只发定位元数据 | `LEGACY_ENV` |

两行「无损」很重要：它们说明**大多数存量其实已经是静态密钥**，只是当年用一个 flag 表达。
把它们照实说成「静态访问密钥」，用户会觉得界面变清楚了，而不是被改坏了。

### 7.2 `LEGACY_ENV` 是什么

来源枚举里的新一档，**只读、不可新建**：

```
LEGACY_ENV · 靠环境身份访问，控制台预览可能失败
这个 catalog 建于 v3 之前，catalog 上没有可用的密钥。服务端读这个位置用的是进程自己的身份，
引擎用的是它自己的。要让它可控，编辑时选一种认证方式并跑一次自检。
```

不自动迁移、不改写存量配置。自动迁移会改掉别人生产环境的取票路径，
而那种改动出错时没有任何人在看。

### 7.3 编辑时的强制补全

打开 `LEGACY_ENV` 的编辑页：

1. 顶部一条横幅（不是提示条，是横幅——它说明这一页保存不了）
2. 方式卡片**都不选中**，右栏给一句「当前配置不在这几种方式里」
3. 保存按钮可用，但点了先跑自检；自检不过不许保存
4. `stsUnavailable` 若还在，不显示成开关，只在「高级参数」里作为一行只读事实

### 7.4 来源枚举收敛

| v2 | v3 | 说明 |
| --- | --- | --- |
| `STS` | `VENDED` | 现签短期凭据（S3 / OSS / Azure / GCS 四条） |
| `RELAY` | `STATIC` | 转发 catalog 上的长期密钥 |
| `NONE` | `LOCAL` | 只剩 `FILE`：自签令牌，不会失败 |
| `NONE` | `LEGACY_ENV` | 新档：靠环境身份，只读 |
| `INVALID` | `INVALID` | 缺字段 / provider 未启用却填了角色 |

`NONE` 之所以必须拆：它原来是「没有密钥」和「本地文件」两个完全不同的东西共用一档，
前者是一个问题，后者是一种正常状态。

## 8. 症状 → 原因

| 症状 | 最可能的原因 | 先看哪里 |
| --- | --- | --- |
| 预览 / 浏览 500，引擎读表正常 | 服务端拿不到凭据：`LEGACY_ENV`、或 provider 没启用 | 来源档位；日志里的 `source=environment` |
| 建表 500，读表正常 | 拿到的是只读票（L2 没通过） | `TableMetadataService` 的 `allowWrite`；自检写档 |
| 引擎读 403，控制台正常 | 键名不对，或没开续期、票已过期 | `/token` 响应体；片段里有没有 `data-token.enabled` |
| 引擎能读、一写就 403 | 写票没做（S1 未落地）或调用者缺 `UPDATE` | §6.3；错误信息里的权限点 |
| 取票 403 且提到 `USE_SECRET` | 静态密钥方式，使用者没被授 `USE_SECRET` | §6.4 |
| 预览时好时坏 | 票寿命 vs 缓存窗口；多实例下各实例寿命不同 | `StorageCredentialCache#cacheUntilMillis` |
| 列目录 403，读单个文件正常 | 表级票被拿去做了 catalog 级动作 | 两条取票入口是否混用 |

## 9. 与现有实现的差距

| # | 差距 | 影响 | 阻塞谁 |
| --- | --- | --- | --- |
| **G2** | 引擎票恒只读（`vend` 三参默认 `false`） | L3 过不去 → 签发档整条不能上线 | **S1（前置）** |
| **G1** | `CatalogCredentialSource` 只有引擎视角的一档 mode | 界面说不出「服务端读不了」 | §7.4 |
| **G3** | `/meta` 不下发 `credential.providers` | 前端无法预知签发档可用性 | §4.3 |
| **G4** | 没有 probe 端点（含写档） | L1/L2 无法在保存前验证 | §5 |
| **G5** | 两条取票路径缓存策略不一致（浏览缓存 / 预览不缓存） | STS 调用量偏高且难解释 | §1.1 |
| **G6** | `AwsStorageConfigInfo` 缺 `sessionToken` | 「临时安全凭证」做不了 | §4.1 第 3 行 |
| **G8** | 存量 `LEGACY_ENV` 无处表达 | 编辑时无法给出「补一种方式」的入口 | §7 |

G2 从 v2 的「一格能力缺口」升格为**前置**：v3 不允许存在「能用一半」的方式，
所以它必须先落地，签发档才有资格出现在列表里。**没有 G2 就把界面做出来，
结果是「能建、不能写」的 catalog —— 这正是 v2 想用红角标警告、而用户要求去掉的东西。**

G7（Azure / GCS 的「不签发」开关）作废：那两个开关原本是用来表达「环境身份」的，
现在没有这一档了。

## 11. 落地顺序

| 步 | 做什么 | 为什么排这里 |
| --- | --- | --- |
| **S1** | 写票按调用者权限签（`vend` 加 `allowWrite`，三个调用点判 `UPDATE`） | L3 的前提。没有它，签发档不许进列表 |
| **S2** | 方式集合裁剪（删环境身份 / 托管标识 / ADC）+ 校验三条 | 依赖 S1 才能保证「列出来的都能用」 |
| **S3** | 来源枚举收敛到五档 + `LEGACY_ENV` + 存量横幅 | 依赖 S2 的方式集合 |
| **S4** | probe 端点（读 + 写两档）+ 保存前自检 | 依赖 S1（复用同一套取票判定） |
| **S5** | 引擎片段补「本方式需要哪个权限点」 | 依赖 S3 的档位信息 |

**S1 单独就能解决「引擎能读不能写」这个长期问题**，而且它不需要产品决策——
它就是权限模型本来该有的样子。建议先做 S1，再动界面。

## 12. 不做什么

- **不做「自动挑一种方式」。** 默认值只由存储类型决定，不从 endpoint 或桶名去猜。
- **不把 probe 做成「保存后静默重试」。** 自检是用户按下的一次动作，不是后台任务。
- **不在前端算档位**（沿用 v1/v2）。
- **不给 Azure 账户密钥、COS 临时密钥。** 规格里没有 / COSN 认证包没有令牌类（G18 实测）。
- **不保留「环境身份」作为高级选项。** 留一个口子等于把 §3 的问题藏起来。
- **不做按 catalog 的签发开关。** 部署级 `credential.providers` + 按 catalog 的方式已经够用。
- **不提供「只读 catalog」开关。** §1.2 已经说明它不成立；如果有人真的需要只读，
  那是授权层的事（不给 `UPDATE`），不是存储配置的事。

| 主题 | v2 | v3 |
