描述权威源
表 / 列注释是唯一权威源，语义模型只存增量（指标、关系、角色、ai_context）。 两个模型引用同一张表时基础描述天然一致——这是防 Semantic Drift 的结构，不是靠人小心。

模型列表 · 设计要点

与「数据保护」同层放治理分组：语义管「怎么理解」，权限管「谁能读」，互不替代。
1挂 catalog 级而不是 namespace 级（与 Polaris 的刻意分歧）：join 关系天然跨库，挂 namespace 要么放不进跨库模型、要么逼人造「语义专用 namespace」。
2每个 expression 必须带至少一个 ANSI_SQL 方言，否则「跨工具一致」退化成「对某方言一致」。控制台默认 strict=true；REST 可宽松存但列表要亮徽标。
3stale 只标不拦：建时 fail-closed 挡新垃圾，读时 fail-open 让旧垃圾可见可修——与血缘 stale 同一哲学。断言：读 stale 模型必须 200，不是 4xx/5xx。
4「无 ANSI 方言」是警告不是错误：Ossie 明确不解释表达式，宽松存是尊重规范；但消费端拿不到可移植表达式，徽标要显式。
5「修复」只对 stale 出现：用当前 schema 重新对照，改完 stale 消失。悬空不产生任何阻断行为。

模型详情 · 设计要点

三个块对应验收断言：结构化视图（可读）、引用状态（stale 可见）、版本审计（谁改的）。
1metrics 必须显示表达式原文 + 方言徽标：语义层的产物是「口径说明书」，原文就是产品本体，任何「美化翻译」都会引入第二个真相源。
2合成描述逐条标注来源（注释 / 模型增量）：drift 的发生面被缩到显式增量，且增量有处可查。
3ai_context 卡片常驻徽标「数据 · 不是指令」：这是提示注入面的 UI 表达，写文案时不能出现「请遵循以下指令」。
4删除要二次确认并记审计；但删除不影响任何查询——语义层 fail-open，表和 SQL 都不依赖它存在。
5freshness 直接用血缘 lastSeen，不新建字段：血缘已实现，这是「比 Polaris 多出的四个杠杆」之一。

编辑与校验 · 设计要点

校验的价值是把「存了垃圾」变成「存不进去」；这是 Polaris 没做的第一件事。
1错误定位到 JSON path：Ossie 文档是嵌套 JSON，整段红字「校验失败」等于没说。四类校验（source / fields / 方言 / 大小）逐条出。
2strict 是请求参数不是全局开关：REST 宽松存保住与规范的边界（不解释表达式），控制台默认 strict 保住人类消费者的可移植性。
3ai_context 用结构化表单：synonyms / examples 是行编辑、instructions 是独立文本域——天然挡住「把指令藏在 examples 里」这类写法的一半。
4409 不自动重试：语义模型是治理对象，两个治理员改同一份口径必须人来裁决，这与 Iceberg 提交并发的取舍不同。
5发布对查询引擎零影响：这条要显式写出来，防止用户以为改口径会动线上数据。

上下文包 · 设计要点

本设计的差异化核心：Polaris 被批评「连哪个模型覆盖哪张表都回答不了」，这是回答。
1五节组织、每节可独立缺失：模型没建、血缘没采集、策略没配，都只是缺一节——不是报错。这是 fail-open 的形状（§5.4）。
2protection 节有标记也不发脱敏列的示例值 / min-max 统计 / 策略原文——把行过滤设计里点名的三个泄露口子全部关掉。
3不可见表的处理是结构性删除而不是打码：schema 没有就是没有，模型没有就是没有，total 不含它——断言 7 直接测这个。
4不让 agent 直连 Ossie 文件（对象存储 / git）：绕过服务端 = 绕过判权和引用校验，还多一个要同步的副本。文件直读只作 P2 离线导出。
5depth 参数控制血缘邻居深度：默认 1，给 agent 的上下文要克制，塞全库语义既贵又稀释重点。

让宿主按字段决定信任级别——MCP 的既有机制，不发明新协议。 提示注入的对策：写入面收窄 + 审计、4 KB 上限、结构化优先、_meta 标注（四条里两条在服务端 P0）。

Agent 接入 · 设计要点

语义层的全部价值来自把口径说明书放在 agent 必经的路上，而不是替 agent 走路。
1第 5 步是铁律：agent 生成的 SQL 与人写的完全同路（授权 → 策略注入）。任何「为好用」开的小灶（凭据、预览、跳过判权）都是把安全面递给自动化。
2MCP server 无缓存无状态：客户端缓存语义会制造第三种失败模式（数据新、语义旧），新鲜度由服务端保证就够了。
3四类 agent 错误 × 四个 Ossie 构件一一对应（口径→metrics / join→relationships / 同义词→synonyms / 角色→dimension）——这不是巧合，ai_context 就是为这个场景设计的。
4失败可定位：第 1 步失败是语义建设问题、第 2 步 403 是权限问题、第 5 步被拦是安全在工作。三方职责在链路上天然分段。
