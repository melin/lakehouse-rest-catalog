# 表详情页（`/tables/:prefix/:database/:table`）

控制台里单张表的操作面。路由三个参数就是 catalog API 的 `{prefix}`、`{database}`、
表名，因此页面上看到的一切与服务端按同一组标识读出的完全一致
——引擎客户端读到的表就是这里显示的表。

整体介绍见 [`console.md`](console.md)，权限判定链见 [`authorization.md`](authorization.md)。
> **Iceberg catalog 下的表不进这一页。** 本页整页建立在 Paimon 协议面的表端点上；Iceberg catalog 的表走平行的 `IcebergTableView`（路由 `/iceberg-tables/...`，详细信息 / 快照 / 文件列表 / 存储优化四个页签），见 [`console.md` §4.7](console.md)。


---

## 1. 数据加载：先取表详情，Paimon 表再取快照

打开页面先发 `getTable`；**要不要再问快照，取决于拿回来的表格式**：

| 请求 | 何时发 | 用途 | 失败时 |
| --- | --- | --- | --- |
| `GET .../databases/{database}/tables/{table}`（`getTable`） | 总是 | 表元数据与 schema | 页面显示错误态 |
| `GET .../databases/{database}/tables/{table}/snapshot`（`tableSnapshot`） | **仅 Paimon 表** | 最新快照统计 | 静默降级为 `null`，统计块不渲染 |

两个请求因此是**串行**的：表格式没有独立字段，只能从 `getTable` 回来的
`schema.options.type` 里读，所以「要不要发第二个请求」必须等第一个回来。
Paimon 表为此多付一个往返；Format / Object / Lance 表则**完全不去碰快照端点**
——那三种表没有快照，请求注定拿不到东西，与其在服务端日志里留下一串
看着像故障的记录，不如不发。

第二个请求刻意容错：没有快照的表（还没写入过数据）本来就取不到统计，
把它当错误处理会让一张空表看起来像坏了。

`overview` 自己**不随挂载自动加载**：路由 watch（`immediate: true`）已经负责首载，
再让 `useResource` 的 `onMounted` 触发一次就是每个表详情页重复发一遍请求——
表详情是控制台最常打开、也最重的读路径，重复的代价不该由它付。

### 1.1 页签随表格式伸缩

表格式（`schema.options.type`，四种取值的语义见
[`catalog-api-endpoints.md`](catalog-api-endpoints.md#建表)）决定这张表有哪些页签——
四种格式里有三种不受快照管理：

| 表格式 | 页签 |
| --- | --- |
| Paimon 表（`options` 里没有 `type`） | 详细信息 / 快照 / 标签 / 分支 / 文件列表 / 数据访问 / 存储优化 |
| Format 表（`type=format-table`） | 详细信息 / 文件列表 |
| Object 表（`type=object-table`） | 详细信息 / 文件列表 |
| Lance 表（`type=lance-table`） | 详细信息 / 文件列表 |

后三种表没有快照，快照 / 标签 / 分支三个页签自然无处可落；「数据访问」在当前约定里
也只随 Paimon 表出现。**Lance 表仍要认出来**：控制台的新建表表单已不给这个入口
（[console-catalog-detail.md](console-catalog-detail.md) §3.5），但 HTTP 与 Spark SQL
还能建出来，认不出它就会被当成 Paimon 表，显示错格式之外还会去问快照端点。详细信息页内部另有两处伸缩：四张快照统计卡片只对 Paimon 表渲染；
「字段列表 / 分区列表」二级页签只在 Paimon 表出现两个（分区状态来自快照提交，
其余表格式没有），**此时才渲染二级页签栏**——只剩字段列表一节时（Format / Object /
Lance 表）不渲染一行只有一个页签的栏，字段列表直接跟着基本信息往下排。
字段列表对三种表都展示：Object 表的列由 Paimon 固定
（`path` / `name` / `length` / `mtime` / `atime` / `owner`），照 schema 展示的是
「这张表实际有哪些列」，与当初有没有手填无关（主键 / 分区字段两列对它恒为「否」，不渲染）。
页面上有一条说明写清少掉的那几个页签去哪了，免得看起来像加载失败。

**页签按需加载。** Paimon 表的七个页签里只有五个需要额外请求，切过去才发：

| 页签 / 二级页签 | 切过去时的请求 |
| --- | --- |
| 快照 | `listSnapshots` |
| 标签 | `listTags` |
| 分支 | `listBranches` |
| 详细信息 → 分区列表（二级页签） | `listPartitions` |
| 文件列表 | `listTableFiles`（`GET /api/console/v1/tables/{tableId}/files?path=`） |
| 存储优化 | `tableOptimizationPolicy` + `tableOptimizationHistory`（一次取齐三块历史） |

「详细信息」（含字段列表）与「数据访问」只用 `overview` 已有数据，不发请求。
已加载过的页签不重复请求，直到点「刷新」或路由参数变化——`reloadAll()` 清空
已加载标记并重载当前页签。存储优化页签的加载请求有一个时序细节（`@tab-change`
在组件挂载前抛出，直接调用会被吞掉），见 [`console.md` §7](console.md) 的说明与
`TableView.vue` 里 `loadOptimization()` 的注释。

## 2. 页签逐个说明（以 Paimon 表为准）

非 Paimon 表只保留其中的「详细信息」与「文件列表」，两页的形态与下表一致。

| 页签 | 数据来源 | 一句话 |
| --- | --- | --- |
| 详细信息 | `getTable` + `tableSnapshot`（分区列表另发 `listPartitions`） | **默认页签**：基本信息 + 快照统计 + 表属性 + 字段列表 / 分区列表 |
| 快照 | `listSnapshots` / `getVersionSnapshot` / `rollbackTable` | 版本号查询、详情、回滚 |
| 标签 | `listTags` / `createTag` / `dropTag` / `rollbackTable` | 把某个快照固定下来 |
| 分支 | `listBranches` / `createBranch` / `renameBranch` / `forwardBranch` / `dropBranch` | 可写的历史线 |
| 文件列表 | `listTableFiles`（控制台扩展端点） | 表目录在存储上的物理内容 |
| 数据访问 | `getTableToken` / `authTableQuery` | 临时凭据与查询级授权规则 |
| 存储优化 | `tableOptimizationPolicy` / `updateTableOptimizationPolicy` / `runTableOptimization` / `tableOptimizationHistory` | 策略配置与执行历史（见 [table-optimization.md](table-optimization.md)） |

**为什么没有「变更」页签。** 控制台曾经有一个变更构造器（选动作、逐条添加、
一次性 POST `alterTable`），现已撤掉：服务端的 `alter` 端点仍在，改表结构请走
HTTP 或 `lakehouse-rest-spark` 的 SQL。理由是表结构变更属于一次性的重决策——
改列名、改类型、删列都没有 undo，而一个「填表 → 攒一批 → 提交」的界面既给不出
预览，也给不出回退，反而让重决策看起来像随手点击。SQL 里同样一步，但是显式的、
可进版本库的、可复现的。

### 2.1 详细信息

页面的默认落点，回答「这是一张什么表」，自上而下四段：

1. **四张统计卡片**（记录数 / 数据文件数 / 数据文件大小 / 最近文件写入，仅 Paimon 表）；
2. **基本信息**：表 ID、是否外部表、表格式、Schema 版本、路径、Owner、创建与更新
   （时间 + 操作者），以及表属性（`options`）的只读 JSON；
3. **字段列表 / 分区列表** 二级页签（原先各占一个一级页签，合并进来后页面短了一层；
   只有 Paimon 表渲染这一栏，分组随表格式伸缩，见 §1.1）；
4. 二级页签各自带**名称过滤**与**本地分页**。

**四张卡片的数从哪来。** 记录数取快照自己的 `totalRecordCount`（提交方每次都会送），
另外三个数**不在快照里**：Paimon 的快照只记清单指针与记录数，文件数与体积另由提交请求随带的
`statistics`（各分区在本次提交里的增量）给出。服务端把这份增量累计到上一个快照的累计值上，
存进 `paimon_snapshot` 的 `file_count` / `file_size_in_bytes` / `last_file_creation_time`，
再由 `getTableSnapshot` 回给页面。三条由此而来的性质：

- **没送 `statistics` 就没有数**（此时卡片显示 `—`，页脚改成「快照未带文件统计」）。
  这与「0 个文件」是两回事——0 是测出来的，空是没测，页面不去猜；
- 未测量的字段（规格里负值表示未测量）不参与累计，与分区列表同一套规则；
- 三个数存**在快照行上**，因此它记的是那一行写入时刻的表级值；同名规则（加法、时间戳取较晚者）
  由 `PartitionService` 一处实现，两级统计不会各算一套。

**为什么合并。** 「这是一张什么表」和「它有哪些字段、哪些分区」是同一个问题，
以前却要切两次页签；分开的唯一收益是每个列表更短，而分页已经解决了长度问题。
合并后 Schema 页签与详细信息页签不再互相重复——表属性（`options`）只在基本信息段
展示一次。

**字段列表**：序号 / 字段名称 / 类型 / 非空 / 主键 / 分区字段 / 描述 / 默认值。
非空与主键、分区字段直接标在行上（数据来自 `schema.primaryKeys` / `partitionKeys`），
不再需要单独一行「分区键：…」让读者自己拿字段清单去对。名称过滤是**本地**的
（字段数有限，客户端包含匹配就够），分页同为本地。**三种表格式都展示这一段**；
Object 表的列由 Paimon 固定（`ObjectTable.SCHEMA` 的六列），主键 / 分区字段两列
对它恒为「否」、不渲染——展示的是这张表实际暴露的列，而不是当初填了什么。

**分区列表**：分区名 / 记录数 / 文件数 / 大小 / 桶数 / 已完成。口径是**最新快照
引用的文件**，各分区之和可能小于仓库实际占用——这条口径说明收进页签名旁的
问号图标（悬停可见），避免一行常驻文字把列表往下顶。分区**按需加载**：切到这个
二级页签才发 `listPartitions`，合并页签不等于把打开页面的成本从两个请求变成三个。
名称过滤同样是本地的。

### 2.2 快照

列出全部快照（快照 ID / 提交类型 / 提交者 / 提交时间 / 总记录数 / 增量记录数），
支持按版本号直查某一版、抽屉里看原始 JSON、以及回滚。
列表里**没有版本列**：定位一个快照用它的 ID 与提交时间就够，版本号只在
「按版本号查询」的输入框、详情抽屉的标题、以及回滚确认框里出现。

回滚确认框写清两件事，因为它们最容易被误解：

- 目标快照**之后**的提交记录会被删除，无法恢复；
- 回滚只移动指针，**不回收数据文件**——它们变成不再被引用的孤儿文件。

页面另外提示：若有客户端正在写入这张表，回滚前应先停止写入。

### 2.3 标签

标签把快照固定下来，使其不受快照过期清理影响。新建时可指定标签名、目标快照 ID
（留空表示最新）、保留时长（如 `7d` / `12h`）与「已存在时忽略」。
回滚到标签与回滚到快照是同一个端点（`rollbackTable` 的 `instant` 判别联合），
差别只在 `type` 是 `tag` 还是 `snapshot`。删除标签后该快照即失去保护。

### 2.4 分支

分支是可写的历史线，常用于隔离试验或并发写入。列表不含主分支。
支持新建（可从某个标签起）、重命名、推进到主分支最新快照、删除。
推进会让该分支上的独立提交变成不可达历史，因此确认框明确写出这一点。

### 2.5 文件列表

表目录在存储上的物理内容：schema 物化写没写出去、快照与清单文件在不在、
有没有失败提交留下的临时文件。与「分区列表」（详细信息页里）互补——那边是
**元数据口径**的统计（最新快照引用了什么），这边是**盘上事实**；
「库里说的」与「盘上写的」对不对得上，两边一比就知道。

三个刻意的取舍：

- **根是表目录，不是仓库。** 调的是 `GET /api/console/v1/tables/{tableId}/files`，
  `path` 相对表目录、`..` 与绝对路径被服务端拒掉，因此这个页签**天生看不了别的表
  与仓库其它位置**。要看整个仓库（包括库里其它表与删表残留）去 Catalog 详情页的
  「文件列表」——根换了一层，换来的就是这个页签不需要先算「表路径相对仓库根是哪一段」。
  两个端点共用服务端同一套列举核心（`CatalogFileService.listDirectory`），
  排序、截断、404/400 语义只有一份。
- **只读。** 与 Catalog 详情页同一理由：仓库里的对象归引擎与服务端自己管，
  手工改文件会让两边对不上，而那正是这页要帮人发现的问题。唯一的例外形状是
  操作列的**下载**（仅文件行有）：同样是把已有字节搬出去的只读操作，
  走 `.../tables/{tableId}/files/download?path=`，流式不缓冲、出不了表目录，
  细节见 [`console-catalog-detail.md` §4.1](console-catalog-detail.md#41-单文件下载)。
- **截断而不是报错。** 目录条目超过 `paimon.rest.file-browser.max-entries` 时
  返回前 N 条并带 `truncated` 标记，页面顶部给出黄条说明；目录优先排序保证了
  被截掉的只会是尾部文件。

交互与 Catalog 详情页的文件列表一致：面包屑（根是「表目录」）+ 目录名可点下钻 +
「返回上级」+ 文件名前缀过滤（回车即重新查询，**过滤在服务端**）+ 表格上的
**本地分页**（服务端一次给一批，默认上限 1000 条）。加载用表的内部 id
（`overview` 里的 `id`），不是库名+表名——那正是 `getTable` 先行的一个理由。

### 2.6 为什么没有权限页签

**授权不在这张表上做。** 表级权限统一到「权限管理」页（`/permissions`）：那里把
作用范围选成 Table 或 View、选好库与对象，就能看到并撤销作用在这张表上的每一条授权，
四级资源（catalog / database / table / view）共用一套表单与一份清单。

此前这一页有过一个「权限」页签，它列的是 catalog 角色携带的授权，并与「权限管理」页
的直接授权分属两个模型、两份清单——同一件事要看两处、撤两遍。现在
Polaris 的 RBAC 面退出控制台（管理面留在管理 API 与 Spark SQL），这一页随之消失，
顺带省掉了它最贵的成本：管理规格没有「按资源反查授权」的端点，那个页签要
先列全部 catalog 角色、再逐个取回 grants 后在控制台侧过滤（N+1 个请求，
且随角色数线性增长）。完整的作用范围与判定顺序见
[`authorization.md`](authorization.md)。

### 2.7 数据访问

两个只读工具：

- **数据访问令牌**（`getTableToken`）：服务端按 catalog 的存储配置下发临时凭据。
  以 `paimon.rest.credential-manager.type=noop` 运行时返回 501，页面如实显示
  ——那种部署下由引擎自带的云凭据链负责鉴权。
- **查询级授权规则**（`authTableQuery`）：传入要查询的列，服务端按调用主体的授权
  返回行过滤表达式与列脱敏规则。两者都在引擎侧生效，控制台只负责展示服务端给出了什么。

### 2.8 存储优化

只对 Paimon 表出现的运维页签，承载[表存储优化](table-optimization.md)的表级配置与
执行历史。四块内容自上而下：

- **总开关卡**：启用开关、调度间隔（分钟）、最近批次（链到「优化任务」页并直接展开）、
  下次调度时间，以及「立即优化」——它产生一个单表批次，走与调度完全相同的
  落库 → 提交 → 跟踪链路。
- **三张动作卡**（Compaction / Snapshot Expire / Orphan File Remove）：每张卡有
  启用勾选与「默认设置 / 自定义」两档。默认档只读展示三层合并后的生效值；
  自定义档是参数表单，保存只提交**改动过的键 + 原本就配过的键**——把整份生效值
  抄成差异等于钉死每个参数，运维之后调 catalog 默认值就再也影响不到这张表。
  字段定义集中在 `utils/optimization.js` 的 `ACTIONS`，与
  服务端 `OptimizationOptions.KNOWN_KEYS` 由校验脚本第 11 组逐字比对。
- **干跑警示**：孤儿清理是三项里唯一删数据文件的，「干跑预览」关掉时页面出一条
  warning，说明清理依据与先干跑一轮的建议。
- **三块历史**：按动作各一块，一次 `GET .../items` 取齐（批次列表不带表级明细，
  逐批拉详情是 N 次请求换一屏数据）。每行带开始时间、批次链接（跳「优化任务」页
  并展开该批次）、状态、指标摘要（`412 → 96 个文件 · 38.4 GB → 36.1 GB` 这类）、
  耗时与失败原因。失败原因（「说明」列）固定**单行、截断省略**，完整内容悬浮
  气泡可见——错误信息动辄一两百字，换行会把一条记录撑成几行的区块，列表就没法
  扫读了。配置在 `utils/optimization.js` 的 `OVERFLOW_TIP`，「优化任务」页的
  批次明细共用同一条规则。

这张表不支持优化（非 Paimon 表 / 外部表，或表在别处被改成外部表）时，页签不显示
表单而是给出原因——「支持但你没开」与「根本不支持」是两句话，页面上都要能说清。

## 3. 破坏性操作

全部走统一的危险确认框（标题 + 目标 + 后果说明），没有「一键直达」的路径：

| 操作 | 后果 |
| --- | --- |
| 回滚到快照 / 标签 | 其后的提交记录被删除，数据文件不回收 |
| 删除标签 | 该快照失去保护，快照过期时可能被清理 |
| 推进分支 | 分支上的独立提交变为不可达 |
| 删除分支 | 只删指针，快照是否保留取决于是否另有标签引用 |
| 删除表 | 元数据与快照历史移除，**数据文件不会自动清理** |

删除表成功后跳回目录浏览页，并保留当前 catalog 与 database 作为查询参数。

页头另有「返回列表」与「刷新」。刷新重载 overview 与当前页签，不重置到默认页签。

## 4. 校验与测试

`scripts/verify-console.py` 有两组直接盯着这个页面：

| 组 | 守什么 |
| --- | --- |
| 8. 对话框状态 | 本页两个 `el-dialog`（新建标签、新建分支）都声明了 `destroy-on-close`，否则编辑会残留上一次的取值；快照详情是抽屉，不受这一组约束 |
| 9. 下拉候选来源 | 页面上的 `el-select` 都必须有 `el-option`/`:options` 之类的候选来源；确属自由输入的（如命名空间）要在源码里写 `el-select-free-input` 标记显式豁免 |

服务端侧 `ConsoleApiTests` 守住静态资源与深链回退。两组守卫都做过**变异测试**：
把修复临时改回去，确认对应用例真的失败，而不是空跑。

## 5. 已知边界

- **不做写入**：不提供 `commitTable`——控制台拼不出一个指向真实文件的快照，
  理由见 [`console.md` §7](console.md#7-端点的取舍为什么没有-committable)。
  本页对快照的介入只有「读」与「回滚」。
- **按表 ID 定位不在这里**：那条路径在目录浏览页（`/browse`），因为它不需要先知道库名。
- **表属性只查看**：`options` 在这张表上只读（「详细信息」里的 JSON 块），
  没有单独的属性编辑器；改属性与改表结构是同一条路——HTTP 或 Spark SQL，
  理由见第 2 节。
