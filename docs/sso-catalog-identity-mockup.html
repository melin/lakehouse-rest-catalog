身份接入

OIDC · 一个 IdP 作为唯一身份源
这一页决定「谁能进来」；不决定「进来能看什么」。 后者由主体与角色决定——见「组映射」。保存前先做一次连通性测试， 重点确认 groups claim 是否真的出现。
1 身份提供方 issuer 必须与发现文档里的一致
Issuer URI *
发现文档从 /.well-known/openid-configuration 拉取；不一致会被拒绝（防 mix-up）。
Client ID *
Audience 强烈建议填
留空不校验受众；同一 issuer 下还有别的应用时，别的应用令牌也能进来。
Scope
要让 groups 出现，通常必须在这里显式加上；Keycloak 还需打开 client 的 group membership mapper。
2 Claim 映射 决定主体名与组从哪来
主体名 claim *
主体名参与授权绑定。用 sub 最稳；可读性由 display_name 补。
组 claim *
通常是字符串数组；单个字符串按一元组处理。精确匹配，不做通配。
显示名 claim P1
只用于列表与审计展示，不参与授权。
3 供给与同步 安全默认
首次登录自动创建主体（JIT） 新建主体没有任何授权，因此默认开启不构成风险；关掉会回到「登录成功但全 403」。
允许接管同名的本地主体 默认关闭。同名 root / admin 若被接管，等于把本地主体的全部授权交给一个 IdP 用户。
登录时同步组 → 角色 只增删 granted_by=IDP 的成员行，永远不动手工授权。
groups 缺失时
ON_LOGIN · 不动（默认）
STRICT · 清空 IDP 角色
OFF · 不同步
默认 ON_LOGIN：很多 IdP 只在特定 scope / 令牌类型里带 groups， 把「这次没带」当成「不在任何组」会在一次配错后削掉所有人的权限。
默认角色 可选
给所有人生成的基线角色。留空是推荐值：先零权限，再用组映射精确给。
改动保存后立即生效，不需要重启

组映射

IdP 组 → principal role · 精确匹配
映射只在登录时生效。 改完不会立刻影响已登录的人；对方下一次登录才会重算。 撤销权限也一样——但授权本身是每请求查库，所以同步过之后立即生效。

为什么不是「组即角色」

IdP 的组名是组织语言（data-eng），catalog 的角色名是权限语言 （editor）。中间必须有一层映射，否则改一次组织架构就要改一遍授权。

401 分三态，不是一句「没权限」

1缺失 · 没带 Bearer，补上即可
2过期 · 去换票或重新登录
3无效 · 签名 / issuer / audience / claim 不对，查服务端日志

登录失败只回分类，不回 claim 原文——避免把 IdP 令牌结构暴露给未认证的调用方。
