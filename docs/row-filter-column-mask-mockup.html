默认语义
没有策略 = 不保护（默认放行）。「取不到策略就拒绝」只发生在策略服务不可达或版本校验失败时， 两者在界面上必须分开表达，否则运维会以为「建了策略就全拦住了」。

策略总览 · 设计要点

列表以「表」为主语，一表一条策略、版本化。
1入口放治理分组，与「权限管理」并列：权限管「谁能读」，数据保护管「读到什么」。两者是同一层治理决策，不该藏进表详情。
2强制等级是部署属性，不是策略属性。徽标只能看不能改——改字段不会让 L0 变 L1（设计文档 §7.1、§2.3）。
3「整列不可见」故意不放入口：注入点晚于 SELECT * 展开，做不了（§5.8）。放一个开关然后默默不生效，比不放更糟。
4悬空策略单独成行样式：DDL 删列后 fail-closed 会把整张表读死，这是事故不是配置。列表必须能一眼看到并「修复」。
5「已停用」与「悬空」用不同颜色：前者是人做的，后者是系统发现的。
6行过滤只显示条件，不显示「命中行数占比」——那本身就是关于数据分布的信息。

新建向导 · 设计要点

四步一条直线，右侧恒有试算——表单与结果同屏，才敢点发布。
1行过滤用结构化构建器，不是自由 SQL。AST 白名单是唯一可校验、可下发的形状；自由 SQL 无法保证「两版 Spark 结果一致」。
2主体范围只给两档（全部 / 指定）。不做「按标签 ABAC」——那是 P2 的事，提前放进来会让人以为已经支持。
3fail-closed 显示为不可编辑的徽标，不是开关。能被关掉的安全默认值等于没有。
4值控件要按列类型换（日期用选择器、枚举列给下拉）。原型里统一成输入框，是为了不把实现细节画死。
5mask 走标准集下拉，参数内联。名字直接用社区 SPIP 的那套（show_last_n 等），将来切官方 API 是改名不是重构。
6「能挡住什么」常驻右栏：用户在这里第一次意识到「直读文件拦不住」，比发布后在告警里发现好。
7NOT NULL + 置空必须逐条勾选确认，默认不勾。硬拒会让「身份证置空」这个最常见需求做不了；默认允许会产出注定失效的策略。
8struct 列置灰并写明「不支持」，不能让用户选中后静默不生效——那是最坏的失败形态。
9发布按钮上带版本号（v9）：策略是版本化对象，操作者点下去之前就该知道自己在改第几版。

注入后的计划

逻辑计划 / 物理计划
逻辑计划（发布前即可看到）
Project […] +- Filter coalesce(and(region=CN, status<>void), false) +- PolicyRelation(v8) +- SubqueryAlias orders +- BatchScan
物理计划（Strategy 展开后）
Project [order_id#11, mask…(customer_phone#12) AS customer_phone#12, null AS id_card#13, hash(email#14) AS email#14, region#4, amount#9] +- Filter (isnotnull(region#4) AND (region#4 = CN) AND (status#5 <> void)) +- BatchScan lakehouse.sales.orders [filters=region IS NOT NULL]
三条不变式：① 所有 mask 在同一层 Project，参数读原值、不链式；② Filter 在 Project 下面， 所以「先脱敏再筛」写不出来；③ 策略行过滤可以下推到 scan（省 IO），用户谓词不能穿过 mask 下推。

策略详情 · 设计要点

这一页回答两个运维最常问的问题：生效了吗、会影响谁。
1头部把「表名 + 状态 + 版本」放在一行：版本号是操作对象，不是元数据。
2编辑不做原地覆盖，直接写「编辑（生成 v9）」——版本化必须体现在按钮上，否则用户以为在改历史。
3「生效证据」直接贴计划片段。这是唯一能自证「配了确实生效」的东西（对应 Kyuubi 那种静默放行的失败模式）。
4表达式的 JSON 给人看也给人复制：排障时运维要把它贴进工单。
5物理计划如实展示，并明说会泄露字面量。假装看不见，用户第一次 EXPLAIN 就会来问。
6「影响面」按入口列，不按组件列——用户关心的是「哪个入口还能看到明文」。
7三条控制台读路径各自给结论（已收口 / 拒绝），不让读者自己推断。
8版本历史保留旧版本，是因为运行中的查询可能还握着旧版本号。
